# Project History

이 문서는 보호구역 자동화 프로젝트를 시작한 뒤 주요 설계 결정, 구현 진척, 운영 이슈를 일자별로 기록한다.
세부 오류 수정이나 개별 SQL 작업이 아니라, 1번 자동화 설계 대화방에서 관리해야 하는 큰 흐름만 남긴다.

## 2026-07-06

- 보호구역 수집, 정규화, DB 적재, 변경 감지의 기본 파이프라인을 점검했다.
- 원본 API 응답, 정제 스냅샷, current 테이블, 변경 이벤트 테이블을 구분하는 구조를 잡았다.
- 종로구 기준 E2E 테스트와 DB 인벤토리 문서를 작성했다.

결정사항: 원본 보관, 실행별 snapshot, current, change event를 분리한다.
이유: 변경 이력 추적과 재검증을 위해 원본과 정제 결과를 함께 보존해야 한다.
다음 작업: 서울 단위 검증으로 확대한다.

## 2026-07-07

- 서울 보호구역 데이터 기준 검증을 진행했다.
- 서울 변경 감지분을 이후 대시보드에서 과거 비교 기준으로 유지하기로 했다.
- 보호구역 변경 이벤트를 신규, 도형변경, 속성변경, 도형+속성변경, 삭제로 구분했다.

결정사항: 2026-07-07 서울 데이터는 초기 비교 기준 중 하나로 보존한다.
이유: 전국 기준선 이전에 이미 감지된 서울 변경분을 잃지 않기 위함이다.
다음 작업: 변경 이벤트 검증과 링크 매칭 후보 검토를 병행한다.

## 2026-07-09 ~ 2026-07-10

- 표준노드링크 기반 보호구역 링크 매칭 후보 검수 케이스를 정리했다.
- QGIS 육안 검수를 통해 외곽도로, 긴 링크, 입체도로, 약한 중첩 등 주요 오탐 유형을 분류했다.
- 자동 확정보다는 후보 생성과 검수 상태 관리가 우선이라는 방향을 확인했다.

결정사항: 링크 매칭은 MVP에서 자동 확정이 아니라 후보 검증 중심으로 둔다.
이유: 보호구역과 도로 링크의 공간 관계가 복잡해 초기 자동 확정은 오탐 위험이 크다.
다음 작업: 검수 버킷과 후보 등급 기준을 보수적으로 유지한다.

## 2026-07-11

- `docs/mvp_project_status.md`를 중앙 상태판으로 두기로 했다.
- 데이터 추출, 취합, 알림은 완료에 가깝고, 후보 매칭은 검증 단계로 정리했다.
- 문서 허브와 대화방별 역할 분리 방향을 잡았다.

결정사항: 1번 자동화 설계 대화방은 전체 설계, 상태판, 문서 허브를 관리한다.
이유: DB, QGIS, 웹, 매칭 작업이 분리되어도 전체 의사결정은 한곳에서 추적해야 한다.
다음 작업: 문서가 추가되거나 역할이 바뀌면 `docs/document_hub.md`를 우선 갱신한다.

## 2026-07-20

- 표준노드링크만으로는 이면도로와 실제 도로 형상을 충분히 대변하기 어렵다고 판단했다.
- NGII 연속수치지형도 도로중심선을 보조 또는 대체 네트워크 후보로 검토했다.
- 전국 통판은 만들되, 검증은 서울/경기와 서울 중심으로 제한하기로 했다.
- 도로중심선은 0.5m 단순화본을 우선 사용하고, 도로명주소 도로구간과 실폭도로는 당장 제외했다.

결정사항: 도로 네트워크 실험은 NGII 도로중심선 중심으로 진행한다.
이유: 도로명주소 도로구간은 경로 탐색 네트워크로 부적합하고, 실폭도로는 면형 데이터라 경로 탐색 전처리 비용이 크다.
다음 작업: 5번 NGII 도로중심선 PostGIS 방에서 원본, 단순화본, 서울 검증을 관리한다.

## 2026-07-23

- 정적 대시보드를 GitHub Pages에 배포하는 구조를 만들었다.
- `dashboard/` 폴더를 `safetyzone.yjkim.dev`에 배포하고, OSM 기반 지도와 통계 확인을 시작했다.
- 전국 기준선 정책을 문서화했다.
- API 429를 피하기 위해 전국 시군구 코드를 청크 파일로 나눠 실행하는 방향을 잡았다.
- API `ERR_03: 0건`은 실패가 아니라 빈 지역으로 처리하고 삭제 비교 범위에서 제외하기로 했다.

결정사항: 웹 지도/통계는 MVP 필수 기능은 아니지만 운영 검수용 정적 대시보드로 먼저 유지한다.
이유: 수집 결과와 변경 이벤트를 눈으로 확인해야 오류와 오탐을 빠르게 판단할 수 있다.
다음 작업: 전국 기준선 적재와 대시보드 export 자동화를 연결한다.

## 2026-07-24

- 모바일 대시보드 레이아웃을 하단 시트 구조로 개선했다.
- Kakao 지도 전환과 Roadview 확인 기능을 추가했다.
- Roadview 패널 드래그, 닫기, 크기 조절, 지도 클릭 기반 재탐색을 추가했다.
- Kakao 지도와 OSM 지도 간 중심과 줌 동기화 문제를 보정했다.

결정사항: 현장 검수성을 위해 Kakao 지도와 Roadview를 대시보드에 포함한다.
이유: OSM만으로는 보호구역 주변 도로, 항공영상, 현장 맥락을 확인하기 어렵다.
다음 작업: 모바일에서 지도와 패널이 서로 가리지 않도록 계속 조정한다.

## 2026-07-25

- 전국 기준선 DB 등록이 성공했다.
- 전국 기준선 등록일의 대량 `NEW` 이벤트는 최근 변경 목록에서 제외하고 현재 객체로만 표시하는 정책을 적용했다.

결정사항: 전국 기준선일의 대량 신규는 운영 변경 이벤트로 보지 않는다.
이유: 실제 신규 보호구역이 아니라 프로젝트 DB에 처음 들어온 기준선 데이터이기 때문이다.
다음 작업: 기준선 이후 일일 실행에서 신규, 변경, 삭제 감지를 확인한다.

## 2026-07-26

- 전국 249개 시군구 기준 일일 실행이 성공했다.
- 수집 20,052건, Polygon 변경 0건, Point 변경 0건으로 확인했다.
- 대시보드 정적 데이터가 전국 현재 객체를 표시하도록 갱신했다.

결정사항: 전국 기준 일일 모니터링은 운영 가능한 수준으로 본다.
이유: 기준선 이후 전체 실행이 성공했고 변경 0건 결과가 정상적으로 기록되었다.
다음 작업: API 한도, 빈 지역, 실패 사유 마스킹, 자동 대시보드 갱신을 안정화한다.

## 2026-07-27

- 대시보드에 Kakao 위성 모드를 추가했다.
- NGII 검수 결과 표시 기능을 대시보드에 붙였다.
- NGII 보호구역 상태, 대표 링크, 검수 도로 레이어 토글을 추가했다.

결정사항: NGII 검수 결과는 별도 탭과 레이어 토글로 관리한다.
이유: 일반 변경 감지와 도로 매칭 검수 정보가 섞이면 패널이 과밀해진다.
다음 작업: NGII 검수 데이터 크기와 로딩 속도를 관리한다.

## 2026-07-28

- 변경 발생 시에만 대시보드 정적 데이터를 갱신하는 자동화 방향을 적용했다.
- 인천 행정구역 개편으로 인한 대량 신규 감지를 일반 `NEW`에서 제외하고 사유를 남기도록 했다.
- 발생일 필터에 맞춰 시도별 변경 요약 칩이 재계산되도록 수정했다.
- 시도별 변경 요약 칩 클릭 시 해당 시도 변경 목록 팝오버가 뜨도록 했다.
- 속성변경 이벤트에 `changed_fields`를 추가해 실제 변경 필드를 카드와 지도 팝업에 표시했다.
- 도형변경 이벤트에 `geometry_change_info`를 추가해 확장, 축소, 형상변경, 면적 차이, 중첩률을 표시하도록 했다.

결정사항: 변경 이벤트는 단순 유형뿐 아니라 검수에 필요한 세부 근거를 함께 보여준다.
이유: 운영자는 `속성변경`, `도형변경`이라는 추상 분류보다 어떤 필드가 바뀌었고 면적이 얼마나 달라졌는지가 필요하다.
다음 작업: 도형변경 정보가 실제 검수 우선순위 산정에 충분한지 확인하고, 필요하면 면적 임계값과 경미 변경 기준을 조정한다.

## 2026-07-31

- 보호구역 운영 DB를 로컬 PostGIS subset에서 Supabase 운영 DB로 이관했다.
- GitHub-hosted runner에서 `chunk_01` 일반 변경감지를 실행해 Supabase 쓰기, 품질검사, 모니터링 이력 갱신이 성공하는지 확인했다.
- GitHub Actions의 09:00 KST schedule은 계속 비활성 상태로 두고, `workflow_dispatch` 수동 실행만 유지했다.
- `prepare_db=false`를 기본값으로 두고, Supabase 운영 DB 준비 migration은 필요할 때만 수동으로 실행하도록 분리했다.
- cloud 모드 일반 수집에서는 migration을 반복 실행하지 않고 `audit-ops-db`로 운영 DB 계약만 확인하도록 조정했다.
- Supabase pooler에서 read-only 세션 상태가 남는 문제를 피하기 위해 DB 연결 직후 `default_transaction_read_only=off`로 초기화하도록 보정했다.
- 변경이 없는 성공 실행 또는 실패 실행에서는 전체 dashboard export 대신 `dashboard/data/overview.json`만 갱신하도록 경량화했다.
- `chunk_01` 일반 변경감지 최종 run은 `Run daily monitor`, `quality-report`, `Export monitoring history`, `Commit monitoring history`가 모두 성공했다.
- GitHub Pages 수동 배포까지 완료해 최신 모니터링 이력이 `safetyzone.yjkim.dev`에 반영되도록 했다.

결정사항: 보호구역 API 수집, 변경 감지, 모니터링 이력, 정적 대시보드만 Supabase + GitHub Actions + GitHub Pages로 온라인 운영한다.
이유: 취업 이후 개인 PC를 계속 켜둘 수 없고, 표준노드링크/NGII/매칭 검수 DB는 대용량 로컬 분석 자산이라 온라인 운영 범위에 넣지 않는 편이 비용과 유지보수 측면에서 안전하다.
다음 작업: 남은 전국 청크를 같은 방식으로 수동 검증하고, 충분히 안정화되면 09:00 KST schedule 재활성화 여부를 결정한다.
